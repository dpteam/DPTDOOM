# DPT.DOOM direct + relay (experimental)

По запросу владельца добавлен альтернативный транспорт для COOP на двоих,
который **не требует входящего соединения к игровому ПК**: host и guest
подключаются исходящими TCP-соединениями к master, оператор которого включил
`--relay`. По умолчанию используется тот же listening port master (например,
25135); `--relay-port` выносит relay на отдельный порт (см. ниже). Без новых
firewall/router rules, UPnP или изменения OpenWrt из приложения.

Это **не исправление NAT, не dedicated simulation server и не произвольный TCP
proxy**. Relay связывает только конкретную зарегистрированную игровую пару.
Игра остаётся TCP lockstep, exactly 2; handshake/game rules/save behavior прежние.

## Использование

Master (relay выключен по умолчанию):

```powershell
dptdoom-master.exe --bind 0.0.0.0 --port 25135 --relay --log master.log
```

Можно сочетать с `--config` для ранее добавленных DNS/manual/API address policies.
Relay не зависит от правильности public game IP в объявлении: это direct
кандидат, а relay endpoint — адрес самого master, к которому уже подключается
launcher. Hairpin source IP роутера остаётся в diagnostic log и не подменяется.

В launcher публикация host добавляет `-net-relay`. Карточка становится
**DIRECT + RELAY** только после того, как master принял outgoing host channel.
Guest выбирает карточку, сохраняет выбранную session identity в памяти launcher
и запускает игру. Сперва пробует direct; при отказе/отсутствии TCP completion
за 2 секунды переключается на relay. Не требует вводить LAN IP. Ручное изменение
адреса/порта/режима или загрузка профиля сбрасывает выбранный relay context.
Session identity не сохраняется в profile INI и не пишется в лог.

CLI:

```text
host:  -net-host PORT -master MASTER_IPV4:PORT -net-relay
guest: -net-join DIRECT_IPV4:PORT -relay-master MASTER_IPV4:PORT -relay-session PUBLIC_ID_HEX32
```

Лаунчер разрешает DNS master в native worker, engine CLI пока numeric IPv4.
`-relay-session` — публичный session ID из свежего LIST, не secret host token.
Запуск plain direct без этих опций не зависит от master/relay.
После успешного TCP direct перехода на relay по ошибке game handshake нет:
нельзя тихо обходить mismatch/desync. При обрыве уже начатой игры reconnect/
переключение транспорта не реализованы; обычный EOF сохраняет survivor world.

Ожидание в launcher увеличено с 30 до **120 секунд** (это всё ещё bounded wait,
не постоянно слушающий игровой сервер). Прямой и relay пути логируют выбранный
транспорт. Во время startup окно показывает штатным HUD-шрифтом из IWAD:
WAITING FOR PLAYER / CONNECTING / TRYING RELAY, вместо пустого framebuffer.
Текст English ASCII: кириллицы в штатном HUD-font нет. Рендер startup не вызывает
HU_Init/I_InitGraphics дважды и не меняет simulation/RNG.

## Отдельный порт relay (`--relay-port`)

По умолчанию relay живёт на порту управления. Этот порт можно разделить:

```powershell
dptdoom-master.exe --bind 0.0.0.0 --port 25135 --relay --relay-port 25136
```

### Лимиты relay

Всё, что ограничивает relay, настраивается флагами (relay остаётся opt-in через
CLI, поэтому и лимиты там же, а не в конфиге):

| Флаг | Диапазон | По умолчанию | Смысл |
|---|---|---:|---|
| `--relay-sessions` | 1..8 | 8 | пар одновременно |
| `--relay-per-source` | 1..4 | 4 | ожидающих хостов с одного IP |
| `--relay-rate` | 4096..1048576 | 65536 | байт/с на сторону |
| `--relay-buffer` | 512..4096 | 4096 | буфер на направление |
| `--relay-idle-seconds` | 10..3600 | 120 | простой спаренной сессии |
| `--relay-lifetime-seconds` | 60..86400 | 21600 | жёсткий предел жизни |

Значения вне диапазона и противоречивые комбинации (`--relay-per-source` больше
`--relay-sessions`, `--relay-lifetime-seconds` меньше `--relay-idle-seconds`) —
**ошибка запуска**, а не тихое зажатие: лимит, который делает не то, что написан,
хуже отсутствующего. Проверка идёт до создания сокетов.

`--relay-buffer` может только уменьшать буфер: он размер фиксированного массива
в слоте пира, поэтому увеличение — изменение на этапе компиляции, а уменьшение
полезно на слабой машине и безопасно, потому что backpressure уже работает от
одного буфера на направление. `--relay-sessions` не может превысить 8 по той же
причине.

Зачем: у управления и relay разные профили нагрузки. Управление — короткие
request/response, где важна задержка и TTL каталога; relay — длительные потоки
с фиксированной полосой. На общем порту они делят listen backlog, лимит активных
соединений и rate limit, поэтому забитый relay ухудшает регистрацию и листинг.

С отдельным портом эти ресурсы действительно раздельные, а не просто «на разных
портах»: у каждой роли свой пул слотов (24 / 8), свой per-IP лимит (8 / 4) и свои
rate buckets (burst 128/24 против 32/4). Разделение фиксированное. Иначе
изоляция была бы декоративной: забитый relay занял бы общий пул и общий burst, и
управление начало бы отвечать лимитом, хотя порты разные. Это проверяется
тестом: флуд на relay-порт не должен мешать LIST, и наоборот.

Роли жёстко разделены, и это не косметика:

- relay-операции (5/6) на порту управления не принимаются, а получают
  редирект на relay-порт (см. ниже);
- операции управления на relay-порту получают `DM_BAD_REQUEST` — отправлять их
  больше некуда, поэтому это обычный отказ.

Ни то, ни другое не заканчивается таймаутом: клиент узнаёт ответ сразу.
События `relay-redirected-to-separate-port` / `control-op-on-relay-port`
пишутся в лог на уровне `relay`, а не как «limit-rejected».

Порт **не** прячется от клиента и не требует настройки у него. Клиент знает
endpoint управления, поэтому мастер отвечает на relay-операцию, пришедшую на
порт управления, статусом `DM_REDIRECT` с двухбайтовым телом — номером порта.
Движок следует редиректу один раз и переподключается туда. Так работают и host
(он публикуется через `-master`, то есть всегда через порт управления, и до
собственной строки в листинге его порт взять неоткуда), и guest.

Почему не поле в LIST: строка целиком занята (0..15 id, 16..19 адрес, 20..23
TTL, 24..155 info, 156..159 flags), расширение строки сломало бы сразу всех
клиентов, а упаковка порта в свободные биты flags заставила бы старых клиентов
отвергать листинг. Редирект не меняет формат строки вообще: при выключенной
опции байты те же, что и раньше.

Launcher ничего не передаёт: `-relay-master` — это endpoint мастера. Клиент,
собранный до этой фичи, увидит неизвестный статус 5 и сообщит об ошибке, а не
зависнет. Настройки `--relay-port` без `--relay` или с портом, равным `--port`,
— ошибка запуска, а не тихий откат.

Отдельные `banlist`/`allowlist` по ролям **сделаны** через `scope` у правила
(`control` / `relay` / `both`, по умолчанию `both`): забитый relay-спамер больше
не лишает доступа к управлению, и наоборот. Проверка allow-списка при старте и
при перечитывании идёт по каждому обслуживаемому порту отдельно. И это
по-прежнему **не** решение проброса порта: наружу нужно открыть тот порт,
который используется.

## Протокол и ограничения

Directory v1 расширен operations 5=RELAY_HOST, 6=RELAY_JOIN, не game v2, и
статусом 5=`DM_REDIRECT` (2-byte тело с номером порта). LIST row offset156:
uint32 flags, bit0=relay available; формат строки не менялся — номер порта в неё
специально не упаковывался. Прежние reserved bits отвергаются. Без `--relay`
новый master отвергает attach. Старый клиент против `--relay-port` получает
неизвестный статус 5 и сообщает об ошибке; ему нужно обновление.

- Host присылает существующие id16+secret24 (40 bytes) и должен совпасть с
  source IP lease. Master проверяет их до передачи владения socket relay.
- Guest присылает публичный id16; требуется уже подключённый waiting relay host.
  Повторный host/guest не может заменить участника. При pairing listing/lease
  потребляются атомарно, вторая гостевая попытка отклоняется.
- Обеим сторонам возвращается обычный 16-byte DPTM success header с нулевым телом,
  после него идут game handshake/tic bytes. До пары game data не принимаются.
  Master не открывает исходящие соединения по указанию клиента.
- Максимум **8 пар**, максимум **4 host-сессии на actual source IP**; waiting
  leases также ограничены directory limits. 4096-byte буфер на направление,
  read backpressure, до 64 KiB/s входящего traffic на сторону/секунду.
  Все четыре значения настраиваются флагами `--relay-*` в пределах, указанных
  выше; по умолчанию они такие же, как раньше.
- Waiting channel зависит от lease и закрывается после remove/expiry; active
  relay больше не зависит от TTL. Idle timeout 120s, hard lifetime 6h.
- Clean EOF дочитывает накопленный буфер и передаёт half-close другой стороне;
  ошибки транспорта закрывают пару. Slow-reader не создаёт неограниченной очереди.
  Buffer/rate/session limits не означают Internet DoS-hardening.
- Логи: attach/pair/close, counters/duration/reason; secrets/id/payload не пишутся.
  Повторяющиеся relay events подчиняются ограничителю логов.

**Без TLS/encryption, peer account authentication, паролей и moderation.** Master
оператор может видеть трафик; публичный session ID позволяет первому гостю занять
место и даже сорвать handshake. Это как публичный direct accept, не приватное
приглашение. Несовместимый guest отклоняется игровым handshake, но слот может
быть потерян до перезапуска host. Не называть relay публично защищённым сервисом.
Использовать с доверенными тестировщиками и осознанным согласием оператора на
bandwidth/CPU; работа server процесса/сети нужна на всю relayed session.

## Проверки

- `master-relay`: настоящий native EXE, opt-in, wrong host auth, guest без host,
  duplicate attach, listing flag, single use, byte-exact transfer > buffer,
  half-close с очередью до EOF, очистка/disconnect/lease remove/capacity.
  Отдельно: dedicated relay port — редирект relay-операции с порта управления
  (статус 5 + номер порта), отказ операции управления на relay-порту, байтовый
  формат строки листинга без упакованного порта, ошибки запуска (`--relay-port`
  без `--relay`, порт равен `--port`), и **изоляция ресурсов**: флуд на
  relay-порт не мешает LIST на порту управления и наоборот. Тест проверен в обе
  стороны: на общей реализации (слоты/лимитеры без разделения) он падает.
- Лимиты relay: значения из `--relay-*` попадают в стартовый баннер, выходят за
  диапазон — ошибка запуска, противоречивые комбинации (per-source > sessions,
  lifetime < idle) — тоже, а понижённый `--relay-per-source` действительно
  отказывает второму ожидающему хосту с того же IP (на общих значениях он был бы
  принят). Тест проверен на падение: с зашитой четвёркой он падает.
- `launcher-windows`: настоящий WebView2 и настоящий master с `--relay-port` —
  host публикуется через порт управления, движок следует редиректу, guest
  приходит по relay; проверяется событие редиректа в master log.
- `master-model`: flags-слово строки остаётся `0`/`1`.
- `master-publish`: настоящие engine/master/guest. Direct-first с relay context,
  недоступный direct endpoint → relay → одинаковые потиковые traces, survivor
  после выхода guest, master outage direct fallback. Startup PPM не весь чёрный.
- `launcher-windows`: карта намеренно указывает TEST-NET direct IP; настоящий
  WebView2 выбирает её и запускает COOP через relay. Без внешних сетей в CI.

Проверено на Windows/MSVC/MinGW/ASan. Новому relay Unix пути нужен следующий CI
run; реальный двухмашинный hairpin/internet gameplay ещё проверить владельцу.
