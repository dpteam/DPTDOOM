# Идеи и цели владельца

Это список требований/направлений, **не список уже работающих возможностей**.
Текущая сеть — экспериментальный direct TCP lockstep ровно на двух игроков.

## Большие серверы: до 1024 игроков

- Цель/план: настраиваемый максимум до **1024 игроков** на сервере.
- Владелец привёл Odamex как ориентир качества и упомянул массовые сессии около
  300 игроков. Это его ориентир, а не проверенный здесь benchmark или заявление
  DPT.DOOM об историческом рекорде.
- Не решается заменой `MAXPLAYERS`: нужны authoritative dedicated server,
  другая модель репликации/interest management, stable object/player IDs,
  bandwidth/CPU budgets, prediction/interpolation, динамические массивы,
  новые save/demo/protocol форматы и нагрузочное тестирование.
- Промежуточные проверяемые этапы: 4 → 8/16 → 32/64 → дальше по измерениям.
  Сотни/1024 — только после реальных профилей и стабильных длительных сессий.
- Двухпользовательский TCP-прототип не считать архитектурой готового 1024-player server.

## Боты DM и COOP

- DM: навигация, поиск оружия/боеприпасов/здоровья, бой, выбор цели и маршрута,
  respawn, уровни сложности, ограничения нечестного знания карты/противников.
- COOP: уметь **проходить игру**, не только следовать/стрелять: ключи, двери,
  кнопки/лифты/телепорты, обязательные триггеры, секреты по политике, выход с карты,
  бой с монстрами и сотрудничество с людьми/другими ботами.
- Нужны navigation graph/mesh и моделирование механик/зависимостей целей,
  восстановление после застревания, тестовые карты/сценарии и replay тесты.
- Scripted headless input в тестах — **не боты**. Нельзя выдавать его за AI.
- Сначала ограниченный DM navigation/combat, затем COOP puzzle progression;
  совместимость с нестандартными WAD/DECORATE потребует дополнительных правил.

## DMFLAGS / правила матча

Минимальное подмножество уже реализовано: `-dmflags 1`/`2`/`3`, описание и
проверки в `docs/NETWORK.md`. Server config/auto/maxplayers остаются идеями.

- Настраиваемые и сверяемые правила независимо от названия режима, чтобы
  менять COOP/DM поведение явно, а не случайными legacy hacks.
- COOP: возможность убрать multiplayer-only оружие, не убирая обычные оружия
  и дополнительных кооп-монстров. В vanilla THINGS флаг 16 общий multiplayer,
  отдельного deathmatch-only бита в этом формате нет.
- Игроки: block/unblock прохождения друг сквозь друга. Это не `noclip` мира,
  не невидимость и не отключение урона/выстрелов между игроками.
- Для будущего серверного config: collision policy `auto|block|pass`.
  В `auto` разрешать прохождение, если **configured maxplayers > 4**, не по
  текущему числу подключённых. Явные `block/pass` должны переопределять auto.
- Сейчас maxplayers фиксирован на 2 и server config отсутствует: auto не
  изображать работающей настройкой, не вводить неиспользуемый `maxplayers`.
- Изменение правил при сохранениях/демо должно быть отражено в новых форматах;
  не ломать vanilla DSG или демо неявными локальными flags.

## Модерация master: banlist и ограничения (план)

Владелец просил записать как будущую фичу. Сейчас мастер **не умеет** банить:
есть только per-IP лимит регистраций (4) и общий cap 128 записей.

- **`banlist.txt`** рядом с конфигом: по строке на правило, `#` — комментарии,
  пустые строки игнорируются. Поддержать: точный IPv4, подсеть CIDR
  (`203.0.113.0/24`), и, если понадобится, диапазон. Явно решить, банить ли по
  TCP source (то, что мастер реально видит) или по advertised IP — это разные
  вещи при NAT/relay, и путать их нельзя.
- Перечитывание файла по SIGHUP/таймеру с атомарной заменой набора, чтобы не
  требовать рестарта; при ошибке разбора — оставить прежний набор и записать
  событие, а не молча применить половину правил.
- Отдельно от бана: **allowlist** режим (`only-allow`) для приватного сервера,
  временный бан с TTL, бан по session-name/host-лейблу как слабая эвристика
  (не доказательство личности).
- Не логировать лишнее: факт бана и правило — да, содержимое пакетов и токены —
  нет. Лимит размера файла и числа правил, чтобы файл не стал вектором DoS.
- Честно документировать границы: бан по IP не защищает от смены адреса,
  NAT-шеринга и relay; это грубый фильтр, а не античит и не auth.
- Для релея: отдельно решить, банить ли source relay-соединения и можно ли
  отказывать в паре по бану одной стороны.

## Duke Nukem 3D как источник фич (правило владельца)

Владелец: брать допфичи и улучшать текущие **из `refs/dukenukem3d-master`**.
Лицензия — GPL v2, совместима с Doom. Уже взято оттуда: сохранение во время
attract-demo.

**Важная граница.** Duke3D — это BUILD-движок: 16.16 fixed point, DOS, x86 asm
(`A.ASM`, `K.ASM`), полностью другая модель мира (sectors/walls/sprites вместо
BSP-секторов Doom). Поэтому переносить нужно **идеи, UX и алгоритмы**, а не код:
скопировать `ENGINE.C` в Doom-рендерер невозможно. Данные `duke3d.grp` под
копирайтом 3D Realms — не распространять.

### Что реально переносимо (по убыванию пользы)

0. **Сделано:** прицел (`crosshair`, пункт CONTROLS → CROSSHAIR), автобег
   (`auto_run`), инверсия прицеливания (`mouseflip`) — всё как настройки, плюс
   подменю CONTROLS по образцу разделения «общие настройки / управление».
1. **Pitch/вертикальный обзор через «y-shearing»** — **СДЕЛАНО (визуальный)**.
   `dpt_pitch_enabled`/`dpt_pitch_max`, мышь и клавиши. Горизонт двигается
   согласованно для `centery` и `yslope[]`; симуляция не затронута (доказано
   совпадением 40-тиковой state-трассы). Осталось как отдельная задача, если
   понадобится: настоящий угол прицела как состояние симуляции (влияет на
   стрельбу и автонаведение) — это уже demo/network state. В Duke3D у
   игрока есть `p->horiz` (угол взгляда), и рендер просто сдвигает виды по
   вертикали; физика при этом плоская. Это дешёвый способ дать реальный
   freelook в софтверном рендерере, не строя 3D. У нас сейчас `novert`
   выключен именно потому, что обзора нет. См. `PLAYER.C` (`horiz`, `horizoff`,
   `aim_mode`) и `GAME.C` (рендер). Требует: угол в player state, сдвиг
   column/span-рендеринга, участие в demo/network state (иначе desync), и
   честного решения по автонаведению оружия.
2. **Прицел (crosshair)** и переключатель прицела горячей клавишей
   (`gamefunc_Toggle_Crosshair`, `ud.crosshair`). Простая, заметная фича.
   **Сделано** как конфиг-настройка + пункт меню; горячая клавиша пока нет.
3. **Автобег (auto-run) как настройка** (`ud.auto_run`,
   `gamefunc_AutoRun`). **Сделано**; отдельная клавиша-переключатель пока нет.
4. **Инверсия мыши по вертикали** (`ud.mouseflip`). **Сделано** (действует при
   `novert 0`, поскольку обзора вверх-вниз пока нет).
5. **Меню/конфиг как данные** — в Duke3D `CONFIG.C` читает и пишет настройки
   через `SCRIPT_GetNumber/PutNumber` по секциям (`Controls`, `Misc`), а не
   сотней индивидуальных биндингов. Для задуманного «кастомного экрана
   настроек» это хороший образец структуры.
6. **Мультиплеерные мелочи:** `MULTI.C` — старый DOS/IPX код, **не переносить**;
   но идеи вроде «кто-то вышел — сессия продолжается» у нас уже есть лучше
   (см. `NET-001`). Ничего нового там не берём.

### Чего НЕ брать

- `MULTI.C`/`MMULTI.C` — DOS-реализация транспорта, у нас свой `dpt_net.c`.
- `A.ASM`/`K.ASM` и любые ассемблерные оптимизации — переносимость важнее.
- Модель мира BUILD целиком — это не «фича», это другой движок.
- Данные/спрайты/звуки Duke3D.

### Порядок работы

Не тащить всё сразу. Каждая фича — отдельный шаг с тестом и честной
формулировкой в документации. Pitch — самый крупный и рискованный (трогает
рендер, demo и network state), поэтому отдельным этапом после того, как
разберёмся с текущей очередью.

## Уже оговорённые идеи

- Snapshot онлайн-игры с загрузкой в single-player. При load в МП сначала
  подтверждение отключения от сервера; отмена ничего не меняет.
- Attract-demo snapshot через F2 уже реализован; держать эту фичу.
- Мастер-сервер, лаунчер клиента/сервера, PK3 с вложенными WAD, DECORATE — см.

## Лаунчер и серверная инфраструктура (владелец)

- P2P-доставка недостающих ресурсов: **PWAD**, а PK3 — только после реализации
  загрузчика PK3. Коммерческие IWAD запрещены. Исключения для базовых данных —
  **Freedoom Phase 1 / Phase 2** и **shareware Doom (`DOOM1.WAD`)**, не полный
  Doom I/Ultimate Doom: allowlist точных версий и заранее проверенных хешей.
  Имя файла/расширение/IWAD header не доказывают права или соответствие версии.
  Хеши не брать из недоверенного объявления peer; официальное происхождение и
  права на распространение каждой версии проверить перед включением в allowlist.
  Для PWAD/PK3 тоже учитывать разрешение автора: не каждый мод можно раздавать.
  Нужны явное согласие на скачивание/раздачу, manifest/order/hash, отдельный от
  lockstep transport, лимиты размера/скорости/диска, safe cache/atomic commit,
  запрет path traversal/исполняемых файлов и автоматического запуска. Это
  будущая функция: сейчас ни P2P, ни PK3 загрузчик не реализованы.

- Диагностика: клиент в Debug — `AllocConsole` вдобавок к файловому логу;
  Release без дополнительной консоли. У master — полезные события одновременно
  в stdout/консоль и файловый лог, с ограничением повторов/ротацией; lease
  secret не логировать, heartbeat не должен бесконтрольно раздувать файлы.
  Реализованы console+file events master с bounded rotation/suppression и
  Debug-client console/tee. См. `MASTER.md` / `TESTING.md`; browser остаётся планом.

- Удобный единый launcher: выбор IWAD/профиля модов, порядок ресурсов, параметры
  клиента/хоста/сервера, понятные ошибки и запуск в один-два действия.
- При подключении сверять **resource manifest/fingerprints** обеих сторон:
  IWAD, каждый PWAD/PK3, каждый применённый DEH/BEX и другие gameplay-affecting
  resources — с размером, порядком, форматом и криптографическим hash. Это
  простой базовый anti-cheat/integrity gate, не полноценный anti-cheat: он
  доказывает совпадение объявленного содержимого, но не защищает от изменённого
  клиента. При mismatch показывать удобный per-file report: missing/extra,
  hash differs, size differs, order differs, suspected corrupted file и путь
  только локально; не логировать лишние данные peer и не принимать peer hash как
  доказательство происхождения. Для разных compatibility levels включать
  versioned subset/manifest schema и отдельно учитывать patch order.
- Автоматически находить `.deh` рядом с выбранными PWAD/PK3 и предлагать их в
  списке подключённых модов по безопасному совпадению имени/профиля. Пользователь
  должен иметь явный крестик/disable для каждого автоматически предложенного DEH,
  ручной порядок и возможность запретить auto-attach для профиля. Не включать
  произвольные DEH молча: показывать источник, hash, preview изменений и итоговый
  ResourceDigest перед запуском; при сетевом подключении всё равно сверять
  фактически применённый manifest.
- Server browser: режим/карта/число игроков/лимит, latency, версия/моды/flags,
  поиск/фильтры, избранное/недавние, прямое подключение без мастер-сервера.
- Master server: регистрация/heartbeat/TTL, проверка доступности, лимиты запросов,
  защита от подмены/спама/amplification; локальное/прямое подключение не должно
  требовать доступности master. Это не то же самое, что игровой dedicated server.
- Текущее standalone C99 directory-ядро — `docs/MASTER.md`; game publication,
  port reachability и launcher browser ещё не подключены. По уточнению владельца
  master и будущий игровой сервер — нативные C/C++, Python только для tests/tools.
- Уточнение владельца: **список серверов прямо в launcher** после реализации
  master; выбор адреса master по IP **или домену**, с редактируемым портом/endpoint.
  Не зашивать один обязательный master. Проверять URL/адрес/разрешённую схему,
  таймауты/DNS и понятные ошибки; direct-connect должен работать независимо.
- Браузер не должен обещать NAT traversal только потому, что сервер найден;
  relay/NAT solution — отдельное решение с ресурсными затратами.

## Мышь, WASD и кастомные настройки (владелец)

- **Реализовано (SDL-бэкенд):** поворот мышью с захватом указателя,
  `mouse_sensitivity`, `grabmouse`, `novert`, `mouse_acceleration`,
  `mouse_threshold`. Захват снимается в меню, на паузе, в demo playback и при
  потере фокуса. Управление по умолчанию — WASD + мышь; стрелки поворачивают.
  Win32-бэкенд мышь ещё не получает (стабы), геймпад не реализован.
- **Остаётся планом:** вертикальный freelook (сейчас `novert` по умолчанию
  включён именно потому, что обзора вверх/вниз нет), настройка в меню игры, а не
  только в конфиге, несколько раскладок (vanilla arrows / WASD / ESDF),
  миграция существующих конфигов без потери пользовательских биндов.
- **Кастомные настройки**: расширяемый экран настроек — видео (масштаб/фильтр/
  vsync), звук (громкости, device), управление (бинды, мышь/геймпад),
  геймплей (авто-переключение оружия, всегда-бег, чувствительность),
  HUD/интерфейс. Валидация значений, сброс к дефолтам по разделу и целиком,
  понятные конфликты биндов (несколько действий на клавишу).
- **ACE DOOM** — источник задумки для настроек/ввода: посмотреть, как там
  организованы экраны, профили и биндинги, что реально удобно. Перед переносом
  кода проверить license/provenance (как и с console/`give`/`summon`), переносить
  идеи и структуру, а не копировать код без проверки лицензии. Не обещать полную
  совместимость с ACE заранее.

## Общение в игре (владелец)

- Общий текстовый чат, затем командный для будущих TDM/командных режимов.
  Нужны явный channel label, team membership/маршрутизация, история/scroll,
  лимиты длины/частоты, mute/ignore. Текущий общий vanilla chat на `T` — база,
  не готовая система каналов. COOP автоматически не выдавать за TDM-команды.
- In-game voice chat: push-to-talk по умолчанию, явный индикатор передачи/приёма,
  выбор микрофона/устройства, громкость, mute/deafen, общий/командный routing,
  optional proximity mode и server policy. Никогда не включать микрофон молча.
- Voice — отдельный канал/очередь от детерминированных ticcmd: codec/jitter
  buffer/bandwidth cap/packet loss, abuse/rate limits и privacy/security design.
  Не засовывать аудиоданные в текущий lockstep, где они задержат симуляцию.
- Unicode/кириллица и локализованный ввод требуют нового font/text-input пути;
  цветные/управляющие последовательности из сети не должны становиться командами.

## Внутриигровая командная консоль (владелец, план)

- Отдельный overlay внутри игры: строка ввода, история, прокрутка, help и
  автодополнение; **не** AllocConsole/терминал Windows и не shell/исполнение ОС.
- Команды вроде **`give`**, **`summon`** и другие игровые/диагностические команды.
  DOOM ACE — кандидат для аудита команд и semantics; наличие конкретных handlers,
  безопасность аргументов и license/provenance проверить до переноса. Не обещать
  полную ZDoom/ACE command compatibility заранее.
- Отделить readonly/local preferences от изменения inventory/world/spawns/map.
  В SP — явная cheat/debug policy; в сети — host/server permissions и доставка
  как согласованное действие на определённом тике. Не изменять локальный мир
  через консоль в обход lockstep/RNG/checksum. Нужны лимиты аргументов/спавнов,
  стабильные actor IDs/типизация, запрет raw pointers и произвольных scripts.
- Define behavior при demos/save/load и ограничениях мода; team/admin/password
  команды зависят от будущей серверной модели. Содержимое консоли не должно
  становиться командами ОС или автоматически исполняться из network chat.

## Профиль и внешний вид игрока (владелец)

- Настройки игрока: имя/цвета/клавиши/аудио/доступность, preview и отдельные
  локальные профили; сверяемые сетевые поля отделить от личных предпочтений.
- Цветные ники: ограниченный безопасный формат, длина, контраст/читабельность,
  fallback без цвета, server moderation и запрет имитации системных сообщений.
- Менять цвет персонажа независимо от сетевого слота; читаемая командная
  идентификация/настройки server/team должны иметь приоритет.
- Скины, включая базовые «как зомби/имп» для humanoid мобов близкого размера.
  Сначала косметика Doomguy с неизменными hitbox/скоростью/оружием; настоящий
  monster-class gameplay — другая фича, не скрытая привилегия скина.
- Проверять frame/rotation/animation/цветовые диапазоны/звуки/размеры ресурсов,
  fallback при отсутствии скина, лицензии ассетов и политику разрешённых пакетов.

## Среднесрочно: DeHackEd и MBF-карты/моды (владелец)

- Стратегия совместимости: сначала довести **classic/vanilla DeHackEd** до
  полного покрытия тех структур и семантик, которые уже существуют в текущем
  DPT.DOOM, не выдавая bounded subset за совместимость со всеми модами. После
  этого расширять поддержку отдельными проверяемыми слоями: BEX/Boom, затем
  MBF, а MBF21 держать отдельным compatibility level. Каждый слой должен иметь
  собственный manifest/fingerprint, compatibility matrix, regression tests,
  headless traces и явные ограничения; не смешивать его незаметно с vanilla
  path и не переносить старые save/demo semantics без нового формата manifest.
- Будущая поддержка **Hexen map format** как отдельный большой этап рядом с
  DECORATE: loader/структура map data, ACS/скриптовые зависимости (если будут
  включены), polyobjects/нативные Hexen specials и изменения world/physics/
  rendering должны проектироваться и тестироваться отдельно. Само чтение
  Hexen WAD не считать совместимостью с игрой.
- Будущая поддержка **DECORATE** для actor definitions как отдельный слой после
  безопасной resource/PK3-инфраструктуры: parser, inheritance, states/actions,
  flags, replacements и deterministic network/save semantics. Не включать
  произвольный код или scripts через DECORATE и не обещать полную ZDoom
  совместимость одним фактом загрузки actor definition.
- Постепенно подтягивать оставшийся подходящий функционал из **csDoom** и
  **DOOM ACE** по конкретным модулям: сначала сравнить behavior и зависимости,
  затем выбрать минимальную нативную реализацию DPT.DOOM. Не копировать целые
  подсистемы вслепую; отдельно проверять license/provenance, notices,
  third-party audio/network code, DOS/address assumptions и отделять parser/
  gameplay от injection/exploit/server infrastructure. Каждый перенесённый
  модуль должен получить собственные tests и не считаться готовым только из-за
  наличия reference source.
- Добавить **DeHackEd**: внешние `.deh` и встроенные `DEHACKED` lumps,
  определённый порядок/приоритет patches, проверка индексов/чисел/строк,
  понятные ошибки, regression tests ванильного пути и изменённых states/things.
  Сейчас `FEATURE_DEHACKED` выключен в `doomfeatures.h`; оставшиеся вызовы/
  заголовки upstream не являются рабочей поддержкой.
- Источники для оценки по просьбе владельца: **DOOM ACE**, альтернативно
  **игровой csDoom**, если реализация нужного модуля там есть и легче переносится.
  В ACE есть `engine/dehacked.*`; README описывает привязку к DOS Doom II 1.9,
  LICENSE — LGPL-2.1. Перед переносом проверить файловые notices/provenance,
  лицензионную совместимость, 32-bit address assumptions и отделить parser/
  gameplay от ACE injection/exploit инфраструктуры. Ни parser, ни MBF/MBF21
  compatibility не считать drop-in. Теперь есть `refs/csDoomNew` и
  `refs/csDoomOld07`: DeHackEd/BEX handlers и отдельные Boom/MBF mechanics найдены,
  но полнота совместимости/безопасность не проверены. `refs/csDoomMaster` —
  по-прежнему только master. Карта источников и смешанные license notices —
  `docs/REFERENCE-SOURCES.md`; заимствования проверять regression tests.
- Поддержать **MBF-совместимые карты/моды**. Это не отдельное расширение файла:
  нужны map specials, физика/AI/flags/action pointers и compatibility semantics,
  а не только принятие WAD в loader. Сам факт открытия уровня не доказывает,
  что он проходим/работает правильно.
- Предлагаемое разбиение для оценки: classic DeHackEd, затем BEX/Boom, затем
  MBF; **MBF21 — отдельный кандидат/этап**, не обещать его автоматически вместе
  с MBF. Владелец отнёс направление к medium; точную матрицу возможностей,
  приоритет и сроки определить после аудита исходников/лицензий и тестовых WAD.
- Сохранить vanilla demo/save behavior и baseline; новый compatibility level,
  patches и изменения gameplay сверять в сетевом handshake/resource manifest.
  Тестировать SP/COOP, headless traces и save/load. Не объявлять поддержку
  всех Boom/MBF WAD по одному успешному тесту. Сейчас это **план**, не фича.

## Будущее: Vulkan и расширенная графика (владелец)

- Vulkan renderer как optional backend при сохранении software fallback и
  возможности headless-тестировать симуляцию без GPU.
- 3D floors, HD replacement textures/sprites, voxel objects, дальнейшие
  улучшения графики и материалов по отдельным проверяемым этапам.
- **Vulkan сам не добавляет 3D floors**: нужны map/sector representation,
  collision, hitscan/projectiles, AI/navigation, sight/sound и compatibility.
  Сначала определить данные/семантику и отделить renderer от world simulation.
- HD/voxel replacements: формат/приоритет/fallback/масштаб/память/GPU limits,
  лицензии ассетов и явное разделение cosmetic vs gameplay-changing пакетов.
- Visual features не должны случайно менять RNG/ticcmd/net state или делать
  сетевую сессию зависимой от FPS/видеокарты. Диагностика GPU и RDP/software
  fallback важны для текущей Windows-среды владельца.

## Дополнительные предложения ассистента (ещё не утверждённые фичи)

1. **Надёжный выход из сети**: disconnect-to-menu, reconnect/resync и сохранение
   причины ошибки вместо закрытия всей игры; UI состояния подключения/таймаутов.
   Active-session disconnect-to-menu уже добавлен; reconnect/startup recovery
   и resync ещё нет, не объединять их в одну «готовую» функцию.
2. **Профили модов и manifest ресурсов**: человекочитаемый mismatch report и
   нужный порядок WAD/PK3; автоматические downloads только с подтверждением,
   лимитами/хешами, sandbox paths и соблюдением прав на game data.
3. **Server administration**: kick/ban/mute/vote, permissions, логирование и
   rate limits до public server browser/voice; anti-abuse не равно обещанию anticheat.
4. **Сетевые диагностики**: ping/jitter/loss/traffic HUD, воспроизводимый latency
   proxy test, детект desync с first-bad-tic report; demos/replays/spectator позже
   строить на версионированных форматах, не на сырых native structs.
5. **Удобный ввод**: remapping, мышь/raw input, чувствительность, optional modern
   controls, gamepad; явные compatibility presets и отдельные regression tests.
6. **Доступность**: text scale/chat visibility, colorblind-friendly team colors,
   subtitles/visual voice indicators, mute по умолчанию для незнакомых источников.
7. **Crash/bug reports**: локальный диагностический пакет с версией/настройками/
   ресурсными хешами, **без** IWAD, личных путей, токенов и содержимого чата/голоса
   без отдельного согласия. `-chat-debug` не включать по умолчанию.
8. **Versioned extended save/demo formats**: сохранить RNG/rules/references для
   online snapshot/ботов/новых карт, явная миграция и сохранение vanilla paths.

Приоритет предложения: сначала стабильный чат/соединение и профили, затем
browser/master, командные режимы/боты/voice; масштабирование и Vulkan — крупные
долгосрочные ветки. Это обсуждаемый порядок, не разрешение реализовать всё сразу.
