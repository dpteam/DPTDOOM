# Тестирование DPT.DOOM

Коммерческие IWAD не распространяются с исходниками. Владелец хранит Doom II
локально в `refs/iwads/doom2.wad`; весь `refs/` игнорируется Git.
Python 3 нужен для smoke tests, но не для сборки игры.
CI без игровых данных и его ограничения описаны в [CI.md](CI.md).

DeHackEd subset: `deh-misc` — data-free parser/rollback/limits/digest;
`deh-engine` — headless с локальным IWAD, synthetic patches/lumps, реальные
health/ammo/capacity, weapon ammo use и two-peer patch mismatch. Это classic
Misc 0 / Ammo / bounded Text (incl. Doom II level names) + BEX [STRINGS]/[PARS]/[CODEPTR] / Weapon frames / Thing numeric/flags/states/sounds / Frame graph+visual+psprite / Infight, не full
DeHackEd/BEX; patched saves используют `DPTDEH1` manifest (тот же набор патчей
обязателен), patched demo — версию 120 с тем же manifest. См. [DEHACKED.md](DEHACKED.md).
Визуальные Frame fields проверяются также по загруженным sprite resources до
уровня; deh-engine сравнивает framebuffer file/lump и отвергает missing frames.
`Unknown 1/2` допустимы только на weapon states и проверяются по точным psprite
`sx/sy`. `Monsters Infight` проверяется по patch report/digest, боевой сценарий
двух видов монстров автоматически пока не воспроизводится.

`map-sky` — Boom/MBF sky transfer (linedef 271/272): временные MAP01 overlays,
разные/повторяемые framebuffer-пиксели и подсчёт затронутых секторов.
`gendoor` — data-free проверка битового layout Boom generalized doors: границы
диапазона, все 512 комбинаций trigger×speed×kind×delay, бит монстра.
`genfloor` — то же для Boom generalized floors: 2048 комбинаций полей,
абсолютные высоты, двойная роль бита model/monster и правила supported-подмножества.
`genceiling` — то же для Boom generalized ceilings: 2048 комбинаций, порядок
ceiling-целей (отличается от floors) и правила подмножества.
`gencrusher` — то же для Boom generalized crushers: 128 комбинаций, отсутствие
утечки старших битов и правила поддержки триггеров.
`genstairs` — то же для Boom generalized stairs: 512 комбинаций и
документированная таблица скоростей (2/4/16/32, не степени двойки).
`genlift` — то же для Boom generalized lifts: 1024 комбинации, таблицы
скоростей/задержек и правила поддержки target-ов.
`genlocked` — то же для Boom generalized locked doors: 1024 комбинации полей и
правила ключей (любой/конкретный/все, режим `sk=ck`, отсутствие смешивания
цветов).
`secspecial` — то же для Boom generalized sector specials: граница 32 (ванильная
vs generalized модель), 1024 комбинации, таблица урона и поддержка
friction/push.
Все `gen*`-тесты также проверяют, что push-триггеры (P1/PR) входят в
поддерживаемое подмножество: BOOM применяет их к сектору за линией.
См. [MAPS.md](MAPS.md).
Не запускать повторный build/test в одном build tree, пока предыдущий не завершён:
Windows может удерживать EXE, а тесты — читать разные версии Python fixtures.

Native master directory собирается вместе с engine (`DPTDOOM_MASTER=ON`).
`master-model` и `master-loopback` — data-free, без окон; второй тест запускает
настоящий C EXE и общается с ним по loopback TCP. Протокол и ограничения —
[MASTER.md](MASTER.md). Python используется только как тестовый клиент.

## Windows: обычная сборка

### Debug-консоль (Windows graphical backend)

Только конфигурация **Debug** для Win32/SDL клиента вызывает AllocConsole, если
нет видимой консоли. Для launcher `CREATE_NO_WINDOW` скрытая console association
сначала отсоединяется. Release/RelWithDebInfo/headless не получают этот код.
`--version` остаётся тихим probe, без консоли и Debug-файла.

stdout и stderr сохраняются отдельно в унаследованных pipes/files; одновременно
обе строки идут в консоль и уникальный `dptdoom-debug-<pid>-<ticks>.log` в CWD игры
(для launcher — `game/profileN/`). Session log launcher не теряется. Relay
выводит строки/блоки до 4096 bytes, без гарантии общего межпоточного порядка
stdout/stderr; при нормальном exit дочитывает хвост. Если файл недоступен, есть
предупреждение в остальных sinks. Это Debug-диагностика: логи не ротируются и
могут содержать локальные пути/сообщения; не публиковать их без просмотра.

```powershell
cmake --build build/windows-sdl --config Debug --target dptdoom
```

`debug-console` — interactive data-free probe реального AllocConsole, больших
stdout/stderr, file/pipe tee и exit flush. `release-console` — отсутствие
дополнительной консоли/Debug-файла. Тесты не меняют реальные профили игрока.

### Обычная сборка

Нужны CMake 3.21+ и Visual Studio 2022 с компонентами C++ и Windows SDK.

```powershell
powershell -NoProfile -File tools/fetch-webview2.ps1
cmake --preset windows -DDPTDOOM_TEST_IWAD="$PWD/refs/iwads/doom2.wad"
cmake --build --preset windows
ctest --preset windows
& ./build/windows/Release/dptdoom.exe -iwad refs/iwads/doom2.wad -warp 1
```

Win32 backend пока без звука. Тест окна проверяет заголовок и `WM_CLOSE`;
он ненадолго открывает игру. Для регулярных проверок использовать headless.

## Windows SDL2: звук и музыка

```powershell
powershell -NoProfile -File tools/fetch-sdl.ps1
powershell -NoProfile -File tools/fetch-webview2.ps1
cmake --preset windows-sdl -DDPTDOOM_TEST_IWAD="$PWD/refs/iwads/doom2.wad"
cmake --build --preset windows-sdl
ctest --preset windows-sdl
& ./build/windows-sdl/Release/dptdoom.exe -iwad refs/iwads/doom2.wad -warp 1
```

Скрипт скачивает **официальные VC development ZIP** SDL 2.32.10 и SDL_mixer 2.8.2,
проверяет фиксированные SHA-256 и распаковывает в `build/deps`. Он не ставит
пакеты глобально и не скачивает игровые данные. Скрипт можно не использовать,
если уже есть совместимые библиотеки: передать `SDL2_DIR`/`SDL2_mixer_DIR` в CMake.
Нужны SDL2 2.0.7+ и, для звука, SDL2_mixer 2.6+.
Сборка копирует `SDL2.dll` и `SDL2_mixer.dll` рядом с EXE. Опциональные codec DLL
не копируются; уведомления о лицензиях — `docs/SDL-LICENSES.txt`.

MSVC Windows-сборка также включает HTML launcher/WebView2Loader.dll, SDK берётся
из отдельного проверяемого fetch. Runtime автоматически не устанавливается.
Engine-only/MinGW: `-DDPTDOOM_LAUNCHER=OFF`. Подробности portable и tests —
[LAUNCHER.md](LAUNCHER.md); `launcher-windows` имеет метку `interactive`.

MUS конвертируется в MIDI в памяти, без общего временного `doom.mid`.
Windows использует доступный native MIDI synth; для других платформ может
понадобиться отдельная настройка синтезатора/патчей. Можно задать
`timidity_cfg_path` в `dptdoom-doom.cfg`; пути к инструментам в таком конфиге
должны быть настроены самим пользователем. Soundfont/Windows MIDI bank не
поставляется с форком. RDP-перенаправление звука должно быть включено до запуска;
если аудиоустройство сменилось, перезапустить игру.

Параметры: `-nosound` — всё аудио, `-nosfx` — только эффекты, `-nomusic` — музыка.
SDL backend поддерживает изменение размера окна, nearest-neighbor scaling и
software fallback. Мышь работает в SDL-бэкенде; геймпады пока не добавлены.

Управление по умолчанию: **W/S** — вперёд/назад, **A/D** — стрейф, мышь —
поворот, стрелки тоже поворачивают. Ctrl — огонь, Space — use, Shift — бег.
Раскладка меняется в конфиге (`key_up`, `key_down`, `key_strafeleft`,
`key_straferight`). Раньше стрейф был привязан к `KEY_STRAFE_L`/`KEY_STRAFE_R`
(0xa0/0xa1) — плейсхолдерам Chocolate Doom, которые SDL никогда не производит,
то есть стрейф фактически не работал.

Мышь настраивается ключами конфига:

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `mouse_sensitivity` | 5 | чувствительность (0..9 в меню) |
| `grabmouse` | 1 | захватывать указатель в игре |
| `novert` | 1 | игнорировать вертикальное движение |
| `mouse_acceleration` | 2.0 | множитель для движений выше порога |
| `mouse_threshold` | 10 | порог, ниже которого движение 1:1 |
| `mouseflip` | 0 | инвертировать вертикаль (действует при `novert 0`) |
| `crosshair` | 0 | прицел в центре вида |
| `auto_run` | 0 | всегда бежать, без Shift |
| `dpt_pitch_enabled` | 1 | вертикальный обзор (y-shearing) |
| `dpt_pitch_max` | 80 | предел сдвига, в пикселях 320×200 |
| `dpt_pitch_aim` | 0 | попадание hitscan идёт по вертикали взгляда; только одиночная игра |
| `use_joystick` | 0 | геймпад включён |
| `joystick_index` | -1 | индекс устройства, -1 = первое доступное |
| `joystick_x_axis` / `joystick_y_axis` | 0 / 1 | оси поворота и движения |
| `joystick_strafe_axis` | -1 | ось стрейфа, -1 = выключена |
| `joystick_*_invert` | 0 | инверсия соответствующей оси |

**Геймпад** (SDL-бэкенд). Код существовал, но был полностью мёртвым по двум
причинам: весь `i_joystick.c` был обёрнут в `#ifdef ORIGCODE`, который
`config.h` явно снимает, а `I_UpdateJoystick` вообще нигде не вызывался. То есть
подключённый контроллер не давал ввода ни при каких настройках.

Теперь реализация под `DPTDOOM_SDL` (Win32/headless получают инертные стабы),
`I_UpdateJoystick` вызывается из `I_StartTic` **после** `I_GetEvent`, чтобы
читать уже обновлённое состояние SDL, и всё это в том же тике.

По умолчанию геймпад **выключен**: молча захватывать устройство ввода хуже, чем
видимый переключатель. Включается в **Options → CONTROLS → GAMEPAD** (применяется
сразу) или `use_joystick 1`. Если геймпад подключён, но выключен, при старте
печатается подсказка, где его включить. Если устройств нет, меню показывает
`NONE`, а не «ON».

`joystick_index` со устаревшим значением (устройство переехало на другой индекс)
не отключает геймпад: берётся первое доступное устройство.

`tests/sdl-joystick.c` гоняет **реальный** путь через виртуальное устройство
SDL: включение/выключение, откат устаревшего индекса, ось, мёртвая зона,
инверсия, кнопки. Регрессию «событие не отправляется» тест ловит.

`mouseflip`, `crosshair` и `auto_run` взяты из user-defs Duke Nukem 3D
(`ud.mouseflip`, `ud.crosshair`, `ud.auto_run`).

**Вертикальный обзор (y-shearing)** — тоже оттуда, где у игрока есть угол
взгляда и рендерер просто сдвигает вид. В Doom эквивалент без изменения
симуляции: двигать линию горизонта. Стены, спрайты и колонки читают `centery`,
а наклон плоскостей — `yslope[]`; обе проекции **обязаны** сдвигаться вместе,
иначе стены «поплывут» относительно пола. Обе считаются одним хелпером
`R_UpdatePitchHorizon`, который вызывается и при смене размера вида, и при
изменении pitch.

Горизонт считается от `centery`. Управление: мышь по вертикали (при
`novert 0`) и клавиши `key_lookup`/`key_lookdown`/`key_lookcenter`
(PgDn/Del/End — уже были в конфиге, но не использовались).

**Pitch и стрельба.** По умолчанию pitch остаётся чисто визуальным: он не
трогает player state, `ticcmd`, демо и сеть, поэтому рассинхронизировать нечего.
Проверено объективно: 40 тиков state-трассы (`-headless-trace`) с
`dpt_pitch_enabled 1` и `0` **побайтово идентичны**.

Опция `dpt_pitch_aim` включает настоящий угол прицела: hitscan идёт туда, куда
смотрит игрок. Это состояние симуляции, но в `ticcmd` его нет, поэтому включённая
опция **сознательно ограничена одиночной игрой**:

- запись демо (`-record`) отказывает при старте: vanilla-формат не хранит pitch,
  и запись воспроизвелась бы с уровнем прицела, то есть показала бы другую игру;
- сетевой старт (`-net-host`/`-net-join`) отказывает: напарник симулировал бы
  чужой выстрел с нулевым наклоном, и получился бы десинк;
- при проигрывании демо и в сети наклон принудительно считается нулевым
  (`demoplayback`/`netgame`), поэтому старые демо и `state-baselines.json`
  остаются валидными, а pitch обнуляется на старте playback.

Угол задаётся **через slope**, а не пикселями сдвига: 80 «номинальных пикселей»
при 320×200 — это ровно тот же угол при любой ширине вида. Иначе прицел совпадал
бы с картинкой только на одном разрешении, а на другом стрельба была бы точнее
или грубее. На 320 пикселях пересчёт — тождество, поэтому вид по умолчанию не
изменился.

Проверки: `pitch-math` (data-free: slope, shear, окно автонаведения, clamp),
`pitch-aim` (движок: при выключенной опции или нулевом pitch трасса побайтово
та же; с наклоном — **другая**; вверх и вниз различаются; `-record` и `-net-host`
отказывают с внятным сообщением; playback не зависит от опции). Тест проверен на
падение: если aim сделать инертным, он падает на «pitched shot must change the
outcome».

Осторожно с формулировкой: при наличии монстров vanilla autoaim может взять одну
и ту же цель для уровня и для наклонённого выстрела (сдвинутое окно всё ещё её
содержит) — выстрел тогда совпадает законно. Поэтому тест идёт с `-nomonsters`.

**Оружие не наклоняется вместе с миром.** Спрайты оружия (psprite) рисуются
через тот же `R_DrawVisSprite`, что и спрайты мира, и берут `centeryfrac` —
поэтому при первом варианте оружие уезжало вместе с горизонтом.

Важно: закрепить только позицию (`sprtopscreen`) **недостаточно**. Рендер
колонки вычисляет текстурные координаты от `centery`
(`r_draw.c: frac = dc_texturemid + (dc_yl-centery)*fracstep`), поэтому при
наклонённом `centery` оружие оставалось на месте, но **сэмплировало не те строки
патча** — содержимое спрайта уезжало из своей формы и читало за границей
патча. Визуально это ровно «форма на месте, а спрайт нет» и подобие HOM при
сильном наклоне.

Поэтому на время отрисовки psprite подменяются `centery` и `centeryfrac` на
неподвижный центр, а после восстанавливаются. Позиция и текстура снова
согласованы. Это же поведение у Duke3D: оружие закреплено на экране,
наклоняется только мир.

Прицел рисуется **после** мира (поэтому не перекрывается спрайтами), в центре
окна вида, а не экрана — при уменьшенном размере вида мир занимает меньший
прямоугольник. Рисуется палитровыми линиями, а не патчем: в IWAD нет лумпа
прицела, а генерировать графику — значит её выдумывать. Он живёт вне
симуляции, поэтому не влияет ни на демо, ни на сетевой checksum.

`auto_run` добавляется к обычной проверке бега (`key_speed`, джойстик), поэтому
Shift продолжает работать, а ходьба остаётся доступной.

Все четыре настраиваются и в игре: **Options → CONTROLS**.

Меню Options рисуется **мелким шрифтом HUD** (тем же, что чат и сообщения), а не
большими патчами IWAD; регулируемые значения — маленькие текстовые полоски вида
`[####.....]`. Причина: патчевая раскладка требовала строк по 16 px от y=37,
из-за чего десятый пункт попадал на y=181 — прямо на статус-бар (его верх
y=168). Мелкий шрифт даёт 10 пунктов по 14 px от y=22, последний заканчивается
около y=156, с запасом до HUD.

Настройки ввода вынесены в подменю **CONTROLS** (SENSITIVITY, ACCEL, VERT MOUSE,
FLIP AIM, GRAB MOUSE, CROSSHAIR, AUTO RUN): тринадцать пунктов на одном экране
не помещаются. Разделение «общие настройки / подробное управление» — по образцу
Duke3D.

Высота строки должна быть не меньше высоты самого шрифта, иначе строки
налезают друг на друга. Первый вариант с 12 px давал именно это — шрифт выше,
и текст двоился. Проверено по кадрам: пункты не пересекаются, HUD не задет.

Два инварианта проверяются на этапе компиляции: число пунктов равно `opt_end`
(иначе чтение за границей массива) и последний пункт помещается выше HUD.

`grabmouse`, `novert`, `mouse_acceleration` и `mouse_threshold` были
задокументированы в `m_config.c`, но ни к чему не привязаны — настройки молча
ничего не делали. Теперь привязаны.

`novert` по умолчанию включён: вертикального обзора (freelook) в движке нет,
поэтому вертикальное движение иначе шагало бы игроком вперёд/назад. Для
классического поведения — `novert 0`.

**Миграция старого конфига.** Сохранённый `default.cfg` перекрывает
компилированные дефолты, поэтому у игроков с уже существующим конфигом WASD
не включался: в файле оставались стрелки и неработающие `KEY_STRAFE_L/R`.
`M_MigrateInputLayout` один раз переписывает **только те бинды, которые всё ещё
равны старому дефолту**, то есть которых игрок не касался; осознанно
изменённые бинды не трогаются. Факт миграции хранится в `dpt_input_version`
(в `dptdoom-doom.cfg`), поэтому повторно она не срабатывает.

Тонкость: старые значения `160/161` (`KEY_STRAFE_L/R`) при загрузке не
восстанавливаются как `0xa0/0xa1` — их нет в таблице scancode-кодов конфига, и
они читаются как `0` («не назначено»). Поэтому миграция считает «старым
дефолтом» и `KEY_STRAFE_L/R`, и `0`.

Захват курсора снимается в меню, на паузе, во время demo playback и при потере
фокуса окна. Это проверяется через `D_GrabMouseCallback`, а не отдельным
состоянием, поэтому не может «залипнуть».

Частые проверки без видимых окон:

```powershell
ctest --preset windows-sdl -LE interactive
```

### Уровни тестов: fast и full

```powershell
ctest --preset windows-headless -L fast    # ~5 с
ctest --preset windows-headless            # полный набор
```

`fast` — метка на быстрых тестах, **не** исключение из полного прогона: обычный
`ctest` по-прежнему запускает всё, поэтому покрытие не уменьшается.

Критерий включения в `fast` — не только секундомер, а отсутствие внешних
зависимостей: тест должен идти в процессе, без IWAD и без запуска игрового
процесса. Тесты master-модели/логов/relay подходят, потому что работают со
своими бинарниками, а не с движком. Тесты, которым нужен IWAD или запуск
`dptdoom`, остаются в полном наборе даже если быстрые: их время зависит от
машины и размера IWAD.

Причина разделения — распределение времени полного headless-прогона
(~381 с на 42 теста):

| Тест | Время | Доля |
|---|---|---|
| `deh-engine` | 135 с | 35% |
| `map-sky` | 95 с | 25% |
| остальные 40 | ~150 с | 40% |

То есть два теста съедают ~60% времени, а все data-free юнит-тесты вместе
занимают около одной секунды. Помеченный набор — 27 тестов за 4.6 с
(headless) и 28 за 4.8 с (SDL). Interactive-тесты в `fast` намеренно не входят.

### Что было оптимизировано

`map-sky` запускал движок ~70 раз, по одному на каждый special, и каждый запуск
заново грузил 15 МБ IWAD. Теперь:

- разбор IWAD кешируется в процессе (`_ENTRY_CACHE`), а не повторяется на
  каждую overlay;
- проверки классификации консолидированы в **одну карту на исход**: 34
  поддерживаемых special-а на 34 односторонних линиях (в MAP01 их 211) и 6
  неподдерживаемых в другой карте. Движок печатает список неподдерживаемых одной
  строкой, поэтому проверка набора сохраняет смысл.

Результат: **95 с → 37.5 с**, полный headless **381 с → 322 с**. Покрытие не
уменьшилось: исчерпывающее декодирование каждого значения остаётся в data-free
тестах `gen*`/`secspecial`, а `map-sky` проверяет именно связку «движок →
отчёт». Убраны только дубли: `hp-light-and-damage` совпадал с `hp-gen-dmg3`.

`deh-engine` так консолидировать нельзя: ~40 запусков, и каждый проверяет
**свой** вывод (разные патчи → разные health/ammo/отчёт). Его стоимость — это
запуски движка, а не подготовка данных.

SDL-тесты ввода используют dummy video, аудио — dummy audio и синтетические
сигналы, не громкоговорители. Они проверяют реальный ненулевой PCM и панораму,
паузы/возобновление музыки, отключение подсистем и ошибку аудиодрайвера.

`sdl-input` дополнительно проверяет мышь: движение без захвата игнорируется,
с захватом накапливается и отдаётся один раз, **удерживаемая** кнопка
репортится ровно один раз (иначе цикл слива событий в движке не завершится),
потеря фокуса сбрасывает зажатую кнопку, а переключение захвата
пересинхронизирует состояние кнопок. Регрессия «DG_GetMouse всегда возвращает
данные» ловится этим тестом.

`sdl-joystick` гоняет реальный путь через виртуальное устройство SDL: включение
и выключение, откат устаревшего индекса, ось, мёртвая зона, инверсия, кнопки.

**Нативный Win32-бэкенд** получает мышь тем же контрактом, но автоматического
теста нет: нужен реальный указатель в реальном окне. Это ручная проверка, и
нельзя считать её выполненной по факту успешной сборки `windows` preset.

`sdl-audio` проверяет панораму на **обоих** крайних положениях (`sep=0` — только
левый канал, `sep=254` — только правый). Оба звука запускаются заново, поэтому
проверяется и первый смикшированный слайс: `I_SDL_StartSound` обязан
зарегистрировать panning **до** `Mix_PlayChannelTimed`. Обратный порядок оставлял
окно, в котором аудиопоток успевал смикшировать начало звука без панорамы
(проявлялось как нестабильный провал на macOS CI, где планировщик попадает в это
окно). Тест детектирует такую ошибку детерминированно, если окно расширить.
Текст `Mix_GetError()` в сообщении о провале помечен как «last SDL_mixer error»:
он может остаться от более ранней пробы (например, отсутствующего MIDI-бэкенда)
и не является причиной падения.

Оконный `net-windows` проверяет peer close → напарник продолжает карту → свой
F7 → меню → SP/save/load; `net-windows-local-end` и `net-windows-guest-end` —
F7 cancel/confirm для обеих ролей, rules/fast/chat/pause handling.
Игровые packet errors проверяются отдельно в fail-fast и menu-recovery режимах.
Тестовый WAV подставляется через штатный механизм music substitutions; это
не доказательство работы аппаратного MIDI на любой машине. Конвертация MUS
проверяется отдельно, а слышимость через RDP подтверждена владельцем вручную.
При заданном IWAD `sdl-engine` прогоняет настоящий движок с dummy video/audio,
проверяет flags/shutdown и graceful failure. Никаких extracted IWAD ресурсов
или сгенерированных WAV не сохраняется в Git.

Тесты с меткой `interactive` открывают окно: обычный `windows-smoke` и
`demo-snapshot` (F2-save в attract-demo, F3-load, переход к живому игроку).
Они выполняются последовательно. Для обычной игры демо-сохранение включено
по умолчанию: дождаться игрового attract-demo, F2 → слот → имя → Enter.
Демо продолжится; F3 загружает сохранённый момент как single-player.
На title/credit screen без игрового уровня сохранение не предлагается.
Применяются ограничения ванильного DSG; это не полный rewind с RNG.

ASan-сборка и реальные границы проверки: [SANITIZERS.md](SANITIZERS.md).
Direct coop loopback/packet/window tests: [NETWORK.md](NETWORK.md).

## Headless

Это отдельный исполняемый файл без создания окна, клавиатуры и вывода звука.
Рендерер Doom работает в памяти; файл **не** является сетевым dedicated server.

```powershell
cmake --preset windows-headless -DDPTDOOM_TEST_IWAD="$PWD/refs/iwads/doom2.wad"
cmake --build --preset windows-headless
ctest --preset windows-headless

& ./build/windows-headless/Release/dptdoom-headless.exe `
  -iwad refs/iwads/doom2.wad -warp 1 `
  -headless-frames 70 -headless-dump build/frame.ppm
```

MinGW/GCC (в текущем PowerShell), Linux/macOS с Ninja:

```powershell
cmake --preset headless -DDPTDOOM_TEST_IWAD="$PWD/refs/iwads/doom2.wad"
cmake --build --preset headless
ctest --preset headless
```

Параметры только headless backend:

| Аргумент | Поведение |
|---|---|
| `-headless-frames N` | Успешный выход после N вызовов вывода кадра, включая кадры wipe-перехода. N — положительное целое. Это не количество игровых тиков. |
| `-headless-dump path.ppm` | Сохранение последнего RGB-кадра в бинарный PPM P6 при завершении. Родительский каталог должен существовать. |
| `-timedemo demo1` | Максимально быстрый прогон встроенного демо. Переход-melt пропускается для воспроизводимого счётчика кадров. |
| `-playdemo file.lmp` | Обычное воспроизведение и успешный выход после демо. |
| `--version` | Версия без IWAD и без инициализации окна (в любом backend). |

Потиковая диагностика, checkpoint/save-load и закреплённые эталоны описаны в
[STATE-TESTING.md](STATE-TESTING.md). `-headless-save-tic` перезаписывает слот 0;
использовать только в отдельном тестовом рабочем каталоге.

При выходе печатается `Headless: frames=... rgb-fnv1a=...`. FNV-1a считается по
RGB-байтам; alpha/padding не участвуют. Это диагностический checksum изображения,
а не полного игрового состояния. Без лимита/демо игра работает до внешней остановки.
`-nogui` и `-nosound` добавляются headless backend автоматически.

**Важно:** исторический `-timedemo` завершает работу через `I_Error`, код
255 / -1 / 4294967295 в зависимости от среды. Успех определяется сообщением
`timed N gametics ...`, а не только кодом выхода. Это не относится к лимиту
кадров и обычному `-playdemo`: они обязаны завершаться с кодом 0.

## Состав smoke tests

- Версия без WAD/дисплея.
- Полный `DEMO1`, в headless — два прогона и сравнение тиков/кадров/RGB.
- Короткое внешнее демо, извлечённое из локального IWAD во временный каталог;
  нормальный выход, корректное сохранение конфигов; headless также проверяет
  чтение изменённой настройки из конфига при следующем запуске.
- Headless: точный лимит кадров, непустой PPM правильного размера,
  неверные параметры и отсутствующий IWAD без всплывающих диалогов.
- Win32: брендированный заголовок и закрытие окна с кодом 0.

При отсутствии `DPTDOOM_TEST_IWAD` CTest запускает тест версии и, для SDL,
самодостаточные тесты ввода/аудио без игровых данных.
Для shareware 1.8 дополнительно передать `-DDPTDOOM_TEST_GAMEVERSION=1.8`.
Скрипты также запускаются напрямую:

```powershell
python tests/headless-smoke.py --exe build/headless/dptdoom-headless.exe --iwad refs/iwads/doom2.wad
python tests/windows-smoke.py --exe build/msvc/Release/dptdoom.exe --iwad refs/iwads/doom2.wad
```

`state-smoke` проверяет save/load и повторяемость трёх демо по каждому тику.
Тесты пока не проверяют сетевую сессию, меню save/load через ввод и совместимость
модов. GCC/MSVC сохраняют ряд legacy-предупреждений Doom;
успешная сборка не означает, что они все исправлены.
